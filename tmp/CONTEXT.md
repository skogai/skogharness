+# Pydantic schema/type system for skogharness
+
+## Context
+
+`skogai-routing` currently validates its Markdown documents against hand-rolled
+JSON Schema files (`.old/schemas/*.json`) plus a bespoke Python validator
+(`_validate_file.py`) that reimplements `jsonschema.Draft202012Validator`
+wiring by hand. The goal is to replace that hand-authored schema layer with
+Pydantic v2 models, so the JSON Schema becomes a generated byproduct of the
+Python types instead of a second artifact to keep in sync by hand.
+
+`skogharness` (`/home/skogix/.local/src/skogharness`) is the new, currently
+empty repo (only a dangling `.claude-plugin/marketplace.json` exists) where
+this gets built from scratch.
+
+Two things fell out of research that change the starting premise:
+
+- **`pattern`, `principle`, and `decision` document types don't actually
+  exist yet.** They're listed as future values in `defs.schema.json`'s `type`
+  enum, but no schema file, section requirements, or shape was ever built for
+  them. Earlier in this conversation, content that looked like real schemas
+  for these types turned out to be from a since-deleted prior session, not
+  the current repo state. This plan does **not** reverse-engineer or invent
+  shapes for `pattern`/`decision`/`principle` — it documents them as an open
+  TODO instead.
+- Separately, OpenWiki's "grounded Claims" model (`Claim`/`Evidence`, with an
+  opaque resolver-owned version-hash token used to detect staleness) is a
+  clean, self-contained data shape that maps directly onto the user's own
+  in-progress `OWNERSHIP.md` staleness idea. Only the data shape is worth
+  porting now — OpenWiki's MCP tool lifecycle, `run.json` checkpointing, and
+  resolve/compare engine are process concerns with no equivalent resolver
+  built yet, and are explicitly out of scope.
+
+The user has reacted badly twice before to over-built proposals (a prior
+`validate.py` + one valid/invalid fixture pair _per type_ + `tests/`
+directory, from a deleted prior session, and an earlier draft of this same
+MVP). This plan is deliberately kept to 8 files, reuses patterns already
+proven in `_validate_file.py` (alias-normalization, a plain type→class
+lookup dict) rather than introducing new Pydantic idioms (discriminated
+unions) that add jargon without adding capability here.
+
+## Ground truth being modeled
+
+From `/home/skogix/.local/src/skogai-routing/.old/schemas/`:
+
+- `defs.schema.json`: `type` enum (`router, workflow, reference, template,
+script, lesson, pattern, decision` — last two unimplemented), `variant`
+  enum, `status` enum, `slug`/`tag`/`xmlSectionName` regex patterns, and
+  `heading`/`link`/`xmlSection` object shapes (a section must carry
+  `content`, `items`, or `table` — never all empty).
+- `frontmatter.schema.json`: only `type` required; everything else optional;
+  open to extra keys.
+- `document.schema.json`: requires `path`, `type`, `sections`; closed to
+  extra keys.
+- Six real per-type schemas, each = `document.schema.json` + a `type` const
+  - "must contain sections named X, Y": `router` (objective, routing),
+      `workflow` (objective, steps, validation), `reference` (overview),
+      `template` (template), `script` (none), `lesson` (checks `headings[].title`
+      instead of `sections[].name`: rule, context, pattern — plus requires
+      `match`/`status`/integer `version` in frontmatter).
+- `_validate_file.py` already normalizes headings/XML tags to canonical
+  section names via a small alias table (e.g. "Purpose" heading and
+  `<objective>` tag both mean `objective`) — this behavior is preserved.
+
+## Files to create
+
+**`shared_types.py`** — the reusable vocabulary every document is built
+from (equivalent of `defs.schema.json`): `DocType`/`Variant`/`Status` enums
+(copied verbatim from the old enums, including keeping `pattern`/`decision`
+as valid _type_ values with no shape built yet), plus `Heading`, `Link`, and
+`Section` models (a `Section` must carry `content`, a list of `items`, or a
+`table` — never all three empty, same rule as the old schema). Also holds
+`SECTION_ALIASES` and `normalize_section_name()`, so "a `## Purpose` heading
+and an `<objective>` tag mean the same thing" lives in one place.
+
+**`documents.py`** — the core file. A `Frontmatter` model (only `type`
+required, extra keys allowed) and a `Document` base model (`path`, `type`,
+`sections` required; extra keys rejected). Six subclasses
+(`RouterDocument`, `WorkflowDocument`, `ReferenceDocument`,
+`TemplateDocument`, `ScriptDocument`, `LessonDocument`), each declaring a
+`required_sections` list, checked by one shared validator on `Document`
+(no six near-identical validators). `LessonDocument` overrides with its own
+validator since it checks `headings[].title` instead and requires
+`match`/`status`/`version>=1`. A `TYPE_TO_MODEL` dict maps a frontmatter
+`type` string to the right class — the same dispatch pattern already used in
+`_validate_file.py`'s `TYPE_TO_SCHEMA`, so nothing new needs explaining. An
+inline comment at `pattern`/`decision` in the enum states plainly: recognized
+as type strings, no shape defined yet, see README TODO.
+
+**`claims.py`** — kept separate because it's a different concern (tracking
+a factual claim and its evidence, not "what does a document look like").
+Two models only: `Evidence` (`resource: str`, `version: str` — an opaque
+token, only ever compared for equality) and `Claim` (`id`, `statement`,
+`evidence: list[Evidence]`). No staleness-recomputation logic, no resolver,
+no MCP lifecycle — those need a resolver design that doesn't exist yet. The
+staleness rule (same token = current, different = stale, unresolvable =
+unresolved) is recorded in the docstring as a note for later, not as code.
+
+**`generate_schema.py`** — runnable script (PEP 723 header,
+`dependencies = ["pydantic"]`, run via `uv run generate_schema.py`). Loops
+over the document models and `claims.py` models, calls Pydantic's built-in
+`.model_json_schema()` on each, writes to `generated-schemas/<name>.schema.json`.
+Makes the JSON Schema a generated byproduct instead of a hand-maintained
+second artifact — run once to compare output against the old
+`.old/schemas/*.json` files by eye.
+
+**`validate_doc.py`** — runnable script (PEP 723 header,
+`dependencies = ["pydantic", "pyyaml"]`, run via
+`uv run validate_doc.py path/to/file.md`), replacing `_validate_file.py` +
+`jsonschema`. Splits frontmatter from a Markdown file with the same
+regex + `yaml.safe_load` approach `_validate_file.py` already uses
+(deliberately not adding the `python-frontmatter` dependency — the existing
+three-line approach is already proven and small enough to explain), scans
+the body for XML tags and headings, normalizes them via
+`shared_types.normalize_section_name()`, looks up the right model via
+`TYPE_TO_MODEL`, and constructs it. Pydantic's own `ValidationError` (which
+names the failing field and why, in plain English) replaces `jsonschema`'s
+error output. Prints `PASS`/`FAIL` plus errors, exit 0/1.
+
+**`fixtures/example-router.md`** — one realistic, valid router document
+(frontmatter `type: router`, both `<objective>` and `<routing>` sections).
+Exists so `uv run validate_doc.py fixtures/example-router.md` has something
+to pass on day one, and doubles as a copy-pasteable starting template.
+
+**`fixtures/example-router-broken.md`** — the same document with the
+`<routing>` section removed, so the same command demonstrably fails with a
+clear "missing required section: routing" message. Together with the file
+above this is a single pass/fail smoke pair proving
+parse → normalize → validate → report works end to end — deliberately not a
+full valid/invalid matrix across all six types (the shape that caused
+friction before). More fixtures get added later only as regression cases for
+real bugs, not speculatively.
+
+**`README.md`** — one paragraph per file above, a "how to run things"
+section (`uv run generate_schema.py`, `uv run validate_doc.py <file>`), a
+plain-language note on the section-alias behavior, and an explicit TODO:
+`pattern`/`decision`/`principle` are known type names with no defined
+document shape — ask Emil what sections they require before adding a model
+for them; don't guess from old chat history.
+
+## Explicitly out of scope for this pass
+
+- No `pyproject.toml` / root package — each script is self-contained via PEP
+  723, matching the ecosystem convention already in use.
+- No `tests/` directory or `pytest` — the two-fixture smoke pair covers the
+  "does the pipeline run" need; a real test suite is a deliberate future
+  addition if/when validation logic grows complex enough to regress silently.
+- No `PatternDocument`/`PrincipleDocument`/`DecisionDocument` — undefined
+  shapes, flagged as a TODO rather than invented.
+- No porting of OpenWiki's Claims _engine_ (resolver, staleness
+  recomputation, MCP lifecycle) — only the static `Claim`/`Evidence` data
+  shapes, since no resolver design exists yet to build the rest against.
+
